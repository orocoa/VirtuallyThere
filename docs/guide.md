# VirtuallyThere 使用与实现说明

[返回 README](../README.md) · [交互架构图](architecture.html) · [项目介绍](introduction.md)

## 从素材开始，而不是从模型参数开始

VirtuallyThere 把创作放在 Codex 对话中。你可以给一段文字、一组照片，或解释照片为什么与你有关。Codex 根据这些内容决定方向，再调用生图和本地工具。

有帮助的信息是：发生了什么、地点或物件有哪些识别线索、你想保留什么，以及大致尺寸和颜色。只提供一张没有背景的照片时，系统能参考可见形状，但不能凭空知道它对你的意义。

下面是输入结构示例，不是真实作品故事：

```text
$virtually-there

素材：我提供的旅行记录与照片。
想纪念的内容：……
希望保留的线索：……
不希望出现的元素：……
偏好：简约、抽象、单色，能看出侧面和背面的体量。
尺寸和刻字：有要求就写；没有则请你选一个方向。
完成后导入 Bambu Studio，切片和打印由我操作。
```

可以只讨论概念，也可以授权一直推进到模型交付。默认自动选方向；是否在概念阶段等你看图，以你当前的要求为准。

## 一次创作怎样推进

### 1. 形成同一份设计 brief

Codex 实际阅读文字、查看图片，把三个层次分开记录：来源中确实存在的线索、如何解释这些线索、用哪些参数实现形体。必须保留的连接、开口、比例或识别点写进同一份要求。

这一步的作用是让后续工作有依据。例如，照片里两道影子的大小与位置是来源观察；把它们转成相连体量是设计解释，不能把设计解释说成对原照片的精确复刻。

### 2. 建立多角度概念参考

每轮至少两张参考板。第一组包含正、右、背视角；第二组以第一组为参考，补充顶、底、前右斜视。Codex 查看输出，核对是否还是同一物件，连接、空隙和刻字有没有矛盾。

AI 概念图不提供精确的三维测量。尺寸和参数以 brief 为准；严格对应实际几何的视图，在模型导出后再渲染。

### 3. 通过 Blender MCP 建模

Codex 编写读取当前 brief 与参数的建模脚本。本地 Python 启动任务自己的 Blender 实例，通过 MCP 执行脚本，构建主体、细节和可选刻字。

可复用的截面、椭球、弧形与布尔操作用于搭建形体；遇到不适合的造型可以编写自由 Blender 脚本。它们是操作工具，不是让所有故事套同一个模型模板。

MCP 依赖随项目的 Python 依赖安装，运行器启动隔离 Blender 并加载配套 addon。默认流程不要求接管用户已有场景。任务结束时只清理自己启动的进程。

### 4. 检查实际导出的模型

几何 worker 检查实际 STL 的闭合性、单体、法向、自交、尺寸、落地和稳定等条件。Codex 查看该 STL 重导入渲染的六视图，逐项记录形体要求是否保留、对应哪个视角、观察到了什么。

几何硬检查失败时，视觉判断不能将它改成通过。修改模型后，旧报告与旧审核不会自动沿用。报告、模型和 brief 通过版本与哈希关联，降低拿旧图确认新模型的风险。

视觉审核仍然是 Codex 的观察，不代表算法能独立理解一段经历，也不保证设计一定符合你的偏好。

### 5. 交付给 Bambu Studio

审核通过后交付 STL、编辑源、六视图、几何报告、清单与预览页。macOS 上可以请求 Bambu Studio 打开 STL，然后观察真实界面确认模型已经导入。

软件返回 `OPEN_REQUESTED` 只表示打开请求发出；它不证明界面导入成功。无法读取界面时，需要如实说明并由用户手动检查。

### 6. 由用户完成实体制作

你在 Studio 中确认机器、耗材、尺寸、朝向、壁厚、支撑与刀路，再执行切片和打印。项目代码没有连接打印机或发送打印任务的命令。

作者使用 P2S 进行实物尝试，这是当前反馈来源之一，并不等于项目已完成所有机型的兼容性认证。打印结果可以作为下一轮修改的输入。

## 路径配置

默认寻找：

```text
/Applications/Blender.app/Contents/MacOS/Blender
/Applications/BambuStudio.app/Contents/MacOS/BambuStudio
```

位置不同时，复制示例配置并编辑路径：

```sh
cp config.example.json config.local.json
```

`config.local.json` 内容示例：

```json
{
  "blender": "/absolute/path/to/Blender",
  "studio": "/absolute/path/to/BambuStudio"
}
```

将 `VT_CONFIG` 设置为该文件的绝对路径：

```sh
export VT_CONFIG="/absolute/path/to/VirtuallyThere/config.local.json"
.venv/bin/python vt.py doctor
```

**运行项目命令的 Codex 进程也需要这个环境变量。** 只在另一个终端里 export，不会自动改变已经打开的桌面应用环境。可以在 Codex 的项目说明中注明配置文件，并让它执行本地命令时传入 `VT_CONFIG`。不要修改整个应用的权限设置。

`doctor` 返回 `ok: false` 时，查看 `paths` 中不存在的文件和 `modules` 中缺失的依赖。它检查路径与导入条件，不替代一次真实建模验证。Python 3.13 及更高版本不在当前声明支持范围内。

## 修改已有作品

| 想改什么 | 处理方式 |
| --- | --- |
| 已有参数的尺寸小改 | 保留已检查概念，新开模型版本，更新对应参数 |
| 形状局部调整，但没有现成参数 | 新开模型版本，局部修改脚本，记录变化 |
| 主体数量、连接方式、开口方向等改变 | 新建 brief，重新生成并审查概念 |
| 已经有模型，想进入检查与交付 | 导入 STL、`.blend` 或 `.3dm` 编辑源及对应的实际模型六视图 |

新模型仍需要检查。已认可方向不必因一次小尺寸修改而从头重做；改变概念结构也不能只换参数绕过概念审核。

## 怎样理解交付状态

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| `MODEL_EXPORTED` | 模型已经导出 | 检查几何和实际模型视图 |
| `GEOMETRY_CHECKED` | 几何硬检查通过 | 完成对应当前版本的视觉审核 |
| `NEEDS_REPAIR` | 检查发现问题或执行失败 | 定位问题、修复并重新检查 |
| `MODEL_READY` | 几何与视觉审核通过 | 交付并进入切片器 |
| `OPEN_REQUESTED` | 已请求 Studio 打开文件 | 看真实界面确认导入 |
| `INTEGRITY_ERROR` | 文件与记录不一致 | 核对版本和文件，不复用失效审核 |

这些状态不表示已打印。手动打印进度应由用户确认或实际照片记录，不能从一个软件状态推断。

## 常见问题

**能只在终端输入一句话就生成吗？**

当前流程依赖 Codex 的阅读、生图和设计判断。CLI 用于执行和记录，没有独立的自然语言设计模型。

**为什么选择简约、抽象的造型？**

这与项目的纪念物审美有关，也让连接、开口、体量等要求更容易在概念与模型之间对照。减少复杂细节是控制建模难度和返工的设计策略；目前没有可通用于所有任务的耗时或 token 节省比例。

**支持 Windows、Linux 或其他切片器吗？**

当前实测为 macOS，自动打开 Studio 的代码仅支持 macOS。其他平台的完整安装与建模流程没有同等验证。交付的毫米 STL 可以由用户尝试导入自己的切片器，但机器、耗材和打印参数需自行确认。

**Rhino 在默认流程里吗？**

默认新建模型使用 Blender MCP。当前提供已有模型的导入接口，可带 `.3dm` 编辑源；不要把这个接口理解成完整验证过的自动 Rhino 创作流程。

**开源是否意味着运行完全免费或离线？**

仓库采用 MIT 许可。Codex 与内置生图能力依赖你使用的服务；实体制作还有耗材成本。项目没有提供独立离线的文字转 3D 模型服务。

**素材会放进公开发布包吗？**

运行资料保存在本地项目输出目录。发布脚本只打包明确列出的源码和文档，不包含私人照片、模型、凭证及本地配置。你交给 Codex 或生图服务的内容仍遵循所用服务的数据处理方式，因此“本地保存产物”不代表所有推理都在本地完成。

**可以承诺拿到就能打印吗？**

交付前有几何检查和视觉审核，但壁厚、支撑、刀路、机器设置与材料都会影响实物。需要用户在切片器中确认并通过实际打印验证。

更多内部命令和文件格式见[执行契约](../skill/references/execution.md)。
